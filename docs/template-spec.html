overlay-launcher Templated JSON Specification

Draft specification for a launcher config format that is JSON-shaped, template-aware, friendly to Windows command lines, and expressive enough for portable app launchers.

Status: implemented config language for the launcher. For code-level rationale, see implementation notes.

1. Design Goals

  • Let a stamped executable launch scripts, programs, runtimes, or modules near itself.
  • Make common portable layout patterns easy: launcher in bin, runtime in python, app code in app, data in data.
  • Avoid conflicts with PowerShell script blocks, Windows batch variables, Bash variables, and common config templating syntaxes.
  • Support ordered environment editing, including reading environment values after prior edits.
  • Support command argument forwarding, indexing, slicing, and list splicing.
  • Keep the language small: no loops, conditionals, arbitrary code, filesystem probing, registry probing, or Lua until the declarative model is proven insufficient.

2. Template Delimiter

The template delimiter is:

@{expression}

The literal escape is:

@@{

Examples:

@{exe_dir}
@{exe_dir:parent:join("python"):join("python.exe")}
@{env:"PATH":prepend_env(exe_dir:parent:join("python"))}
@@{exe_dir}

Bare braces are not special. This means PowerShell script blocks such as Where-Object { $_.Name -eq "python" } remain ordinary text.

Any occurrence of @{...} is treated as an intended launcher template. If it cannot be parsed, the config must fail with a clear error. This avoids silent ambiguity. Users who need literal @{ write @@{.

3. Example Config

{
  "terminal": true,
  "cwd": "@{exe_dir:parent:join("app")}",
  "env": {
    "PATH": "@{env:"PATH":prepend_env(exe_dir:parent:join("python"))}",
    "PYTHONHOME": "@{exe_dir:parent:join("python")}",
    "PYTHONPATH": "@{exe_dir:parent:join("app")}"
  },
  "command": [
    "@{exe_dir:parent:join("python"):join("python.exe")}",
    "-m",
    "my_module",
    @{args}
  ]
}

The source file above is templated JSON, not strict JSON. The raw @{args} array item and the unescaped quotes inside template expressions become valid only after the launcher preprocessing pass.

Inside @{...}, write template string arguments normally: join("python"), not join(\"python\"). The first pass consumes the whole template expression before the JSON parser sees the file.

JSON object keys are not templated. Keys must be literal config keys or literal environment variable names. Template expressions are evaluated in values and array element positions only.

5. Lookups

Lookups pull values from dynamic data rather than fixed launcher metadata.

Environment Lookup

@{env:"PATH"}
@{env:"LOCALAPPDATA"}
@{env:"PATH":prepend_env(exe_dir:parent:join("python"))}

Environment names are string arguments, not predetermined identifiers. This keeps the distinction clear: env:"PATH" means lookup the current value of PATH.

Argument Lookup

@{args:1}
@{args:2:filename}
@{args}
@{args:from(2)}
@{args:take(10)}

Argument lookup is 1-based. args:1 is the first user argument passed to the launcher. There is no args:0 in the argument lookup family. Use args0 for the launcher invocation name/path, or exe_path for the resolved stamped executable path.

7. Element Injection

Most template expressions produce a value that can be placed inside a JSON string. Some expressions, especially args, produce multiple string elements. Those multi-element expressions can only expand at an array position where they can become several array elements. 

{
  "command": [
    "@{exe_dir:parent:join("python"):join("python.exe")}",
    "-m",
    "my_module",
    @{args}
  ]
}

If the launcher is run as:

tool.exe --input file.json --verbose

The final command becomes:

[
  "C:\\Bundle\\python\\python.exe",
  "-m",
  "my_module",
  "--input",
  "file.json",
  "--verbose"
]

Implementation detail: pass 1 turns @{args} into a UUID string such as "342b8d59-0511-456e-b605-19794be53805". During evaluation, if an array item is exactly that UUID string and the expression returns a list, that UUID string item is removed and the returned strings are inserted at the same location.

A list expression inside a larger string is an error. For example, "prefix @{args} suffix" would become one JSON string containing a UUID plus other text, and there is no sensible way to replace part of one string with several command arguments.

8. Evaluation Order

Evaluation happens in the user's frame of reference: top to bottom through the parsed config, preserving source order for JSON objects as parsed by Zig's current dynamic JSON representation.

  1. Collect initial launcher metadata: executable paths, original cwd, user args, platform values.
  2. Collect inherited environment into the mutable environment lookup.
  3. Resolve top-level fields in source order where meaningful.
  4. When an environment key is resolved, immediately write it into the environment lookup.
  5. Expressions evaluated later can read values written earlier.
  6. The final command array is resolved after environment edits, so @{env:"PATH"} sees the final PATH.
{
  "env": {
    "PATH": "@{env:"PATH":prepend_env(exe_dir:parent:join("python"))}",
    "PATH_AFTER": "@{env:"PATH"}"
  },
  "command": [
    "cmd.exe",
    "/C",
    "echo @{env:"PATH_AFTER"}"
  ]
}

In this example, PATH_AFTER sees the edited PATH, and the command sees both edits.

JSON objects are unordered by the JSON specification. This format intentionally defines source-order semantics for overlay-launcher config, relying on the chosen parser preserving insertion order. Arrays remain the clearer choice when order is critical or when future portability matters.

9. Processing Passes

Pass 1: Template-Aware Scan

The launcher scans the raw bytes before JSON parsing. It produces strict JSON plus a sentinel table.

  1. Scan raw config bytes from left to right.
  2. When @@{ appears, emit literal @{.
  3. When @{ appears, enter template scan mode.
  4. Inside template scan mode, } ends the expression only when not inside a quoted string and not inside parentheses.
  5. Quoted strings inside templates follow JSON string escape rules.
  6. Replace the complete template expression with a fresh random UUID string.
  7. Store uuid -> raw expression and whether the expression appeared inside a JSON string or as a raw JSON value.

Input:

"PATH": "@{env:"PATH":prepend_env(exe_dir:parent:join("python"))}"

Strict JSON after pass 1:

"PATH": "bed78636-c5a1-4cfd-aeb3-4ec810c5b695"

Sentinel table:

bed78636-c5a1-4cfd-aeb3-4ec810c5b695
=> env:"PATH":prepend_env(exe_dir:parent:join("python"))

Pass 2: JSON Parse

The output of pass 1 is strict JSON and can be parsed using the normal JSON parser. Syntax errors at this point are JSON errors in the transformed document, but error reporting should point back to original source offsets where possible.

Pass 3: Config Walk And Evaluation

Walk the parsed JSON tree in source order. When a string equals or contains UUID sentinels, evaluate the associated expression and replace it.

  • If a sentinel expression returns a string, it can replace a whole string or part of a string.
  • If a sentinel expression returns a list, the parsed JSON value must be an array item that is exactly the UUID string. The UUID string item is dropped and the returned list elements are inserted at that location.
  • Object keys are not templated. A sentinel in an object key is a config error.
  • If a list expression is found inside an object value string or partial string, raise an error.
  • When resolving env, write completed env values back into the mutable lookup immediately.

10. Expression Parsing

The expression parser should be a small tokenizer plus recursive-descent parser. Ad hoc string splitting will become fragile once quoted strings, parentheses, and nested expressions exist.

Token Types

TokenExamples
Identifierexe_dir, parent, prepend_env
Integer1, 10
String"PATH", "python.exe"
Colon:
Open paren(
Close paren)

Grammar Sketch

expression      = source ( ":" transform )*

source          = identifier
                | "env" ":" string
                | "args" ":" integer
                | "args"

transform       = identifier
                | identifier "(" argument ")"

argument        = expression
                | string
                | integer

There is no comma token because functions take at most one extra argument. That is an intentional scoping decision.

Evaluation Algorithm

  1. Parse the source and resolve it to a typed value: string, integer, or string list.
  2. For each transformation, check that it accepts the current value type.
  3. If the transformation has an argument, recursively evaluate that argument expression.
  4. Apply the transformation and produce a new typed value.
  5. At the end, return the typed value to the JSON tree walker.

Example:

env:"PATH":prepend_env(exe_dir:parent:join("python"))
  1. Resolve env:"PATH" from the mutable environment lookup.
  2. Parse argument expression exe_dir:parent:join("python").
  3. Resolve exe_dir.
  4. Apply parent.
  5. Apply join("python").
  6. Apply prepend_env(argument) to the original PATH value.
  7. Return the edited PATH string.

11. Error Design

The launcher runs programs. Silent wrong behavior is expensive. Prefer explicit, actionable errors for malformed templates and unsafe list contexts.

CaseRecommended BehaviorReason
Invalid @{...} syntax Error with hint to escape literal @{ as @@{. Every @{...} is intentional.
Unknown base value Error. Invalid template expression.
Unknown transform Error. Invalid template expression.
Wrong transform type Error. Example: args:parent is nonsensical.
Missing environment variable Return empty string by default. Matches common environment expansion behavior and helps portable configs.
Missing required environment variable Future transform: required can turn empty into error. Allows strictness where needed.
args:10 out of bounds Return empty string by default. Error when error_on_arg_out_of_bounds is true. Optional forwarded args are common, but strict mode can catch bad invocation.
Arg slice beyond end Clamp to the available args. If the slice starts beyond the end, return an empty list. args:take(10) works with fewer than 10 args; args:from(999999) inserts nothing.
List expression inside partial string Error. Cannot inject many elements into one string.
Unclosed template expression Error with source location. Template syntax error.
Unclosed string inside template expression Error with source location. Template syntax error.

Optional Strictness Controls

{
  "error_on_missing_env": false,
  "error_on_arg_out_of_bounds": false
}

When error_on_missing_env is false, missing environment variables resolve to an empty string. When error_on_arg_out_of_bounds is false, single-argument lookups such as args:10 resolve to an empty string if the argument is not present. List slicing always clamps naturally.

12. Implementation Notes

Sentinels

Use fresh random UUIDs for sentinels, not predictable names like __ZL_EXPR_0001__. This avoids accidental and malicious collisions with user text.

Source Locations

Each sentinel table entry stores the original byte range. Template parse errors can point directly to the original @{...}. JSON parser errors after pass 1 are not yet remapped back to original template-source offsets.

Duplicate JSON Keys

Duplicate object keys are a config error and must be rejected. Ordered evaluation becomes ambiguous if the same key appears twice.

Object Order

The current Zig dynamic JSON path preserves insertion order through its object map implementation, and env arrays are available when order is part of the config contract. If source-order semantics remain important to this format, the project should keep using a representation that preserves iteration order.

Cross-Platform Path Policy

Some names and transforms are currently Windows-flavored, such as exe_drive, program_files_dir, and Windows drive/root handling. Keep them in scope for now, but define OS-specific behavior before promising full Linux or macOS compatibility.

Typing

The evaluator should use explicit value types:

String
StringList
Integer

This makes list splicing, wrong transform errors, and argument transform checks much cleaner than treating everything as text until the end.

13. Validation Of The Approach

The approach is viable. It keeps the config readable, avoids PowerShell brace conflicts, supports ordered environment mutation, and gives argument forwarding a clean list-splice model.

Strengths:

  • Clear delimiter: @{...} is rare enough in ordinary commands and easy to escape.
  • Valid strict JSON after preprocessing, so the main config tree can use normal JSON tooling internally.
  • Small deterministic expression language, not a general scripting language.
  • Environment edits can be read by later expressions.
  • Argument list injection is explicit and type-safe.

Risks:

  • The source file is templated JSON, not pure JSON. Generic JSON editors may complain about raw array splices and raw quotes inside templates.
  • Relying on JSON object order is a format-level choice and should be documented loudly.
  • Path transforms must be OS-correct. Windows drive/root/UNC behavior matters now, but Linux and other platforms should not be painted into a corner.
  • Error messages need to be excellent, because this config runs at application launch time.

Recommendations

  • Keep the first version strict and small: no conditionals, no loops, no filesystem checks.
  • Keep scanner, expression parser, config-walk, and launcher smoke coverage broad as new cases are added.
  • Add more golden tests when platform-specific path behavior expands beyond the current Windows-focused coverage.
  • Consider offering a strict JSON alternative for complex expressions later, such as { "expr": "..." } or { "splice": "args" }, but do not start there unless editor compatibility becomes a real problem.
  • Keep Lua or another embedded language as a later escape hatch only if users need conditionals, discovery, registry access, or fallback chains.

Open Questions

  • Should any portable-layout convenience bases be added later, or should users compose them from exe_dir and path transforms?
  • Are the top-level strictness flags enough, or should individual expressions be able to opt into required values?
  • Should missing single-argument lookups always honor error_on_arg_out_of_bounds, or should a separate optional-arg helper exist later?
  • Should source-order object evaluation be allowed everywhere, or only in specific objects like env?
  • Should the command array support only strings and list splice expressions, or also structured command fragments later?
